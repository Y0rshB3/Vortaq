# Vortaq

Independent, open-source desktop database client (macOS first, also Windows/Linux; MySQL, MariaDB, PostgreSQL, SQLite and MongoDB, all regular engines since 2.0.0). Version line: ElectronDB ended at 0.1.9; this product is Vortaq 2.0.0 onwards that can import Navicat data (connections, batch jobs, `.nb3` backups). Spanish UI, English code and comments. Formerly called **ElectronDB** and, before that, **Navidog**; the GitHub repository and the repo folder still use the old names.

## Commands

- `npm run dev` — Electron + Vite dev mode
- `npm run check` — lint + typecheck + unit tests (must pass before finishing any task)
- `npm test` / `npm run test:watch` — Vitest (projects: `node`, `web`)
- `npm run test:integration:required` — the gate: MySQL and backup suites against MySQL 8.4 (`VORTAQ_TEST_MYSQL_URL=mysql://root:navidog@127.0.0.1:33306/navidog_test`) and 5.7 (`VORTAQ_TEST_MYSQL57_URL=mysql://root:navidog@127.0.0.1:33357/navidog_test`) the MariaDB fixes against MariaDB 11 (`VORTAQ_TEST_MARIADB_URL=mysql://root:navidog@127.0.0.1:33311/navidog_test`) the PostgreSQL suite against PostgreSQL 17 (`VORTAQ_TEST_PG_URL=postgres://postgres:navidog@127.0.0.1:55432/navidog_test`) and the MongoDB suites (`mongo`, `vqbMongo`, `aiMongo`) against MongoDB 8.2 standalone with auth (`VORTAQ_TEST_MONGO_URL=mongodb://root:navidog@127.0.0.1:57017/?authSource=admin`) and a single-node replica set for transactions (`VORTAQ_TEST_MONGO_RS_URL=mongodb://127.0.0.1:57018/?replicaSet=rs0`, compose services `mongo82`/`mongo82rs`; the replica set needs one `rs.initiate`, see the compose file; pin `mongo:8.2`); a missing URL fails the run. The SQLite suites (`tests/integration/sqlite*.test.ts`, `vqbSqlite`, `aiSqlite`) need no server: they use real files in a temp folder, in-process workers, and one real child process (esbuild-bundled `src/main/sqlite/nodeWorker.ts`) for cancel-by-kill. `VORTAQ_TEST_SSH_URL=ssh://vortaq:navidog@127.0.0.1:52222` (compose service `sshd`) is optional and turns on the PostgreSQL SSH-tunnel test. `VORTAQ_TEST_MARIADB_OLD_URL` (a throwaway `mariadb:10.11` or `mariadb:11.4` container, never on 3306/3307) is optional and turns on `mariadbCrossVersion` (versioned history between the 2038 and 2106 TIMESTAMP ranges). Servers: `docker compose -f tests/docker-compose.yml up -d --wait`. Version-specific expectations are marked `5.7 split` in the tests; add one only for a real server difference, never to loosen an assertion.
- `npm run test:integration` — same suites, but a server without its URL is skipped. The macOS keychain test also needs `VORTAQ_TEST_KEYCHAIN_DIR=<scratch dir>`: it creates a throwaway keychain there and deletes it.
- `npm run build` — production bundle to `out/`; `npm run dist` — installers in `release/`
- Smoke test after a build: `VORTAQ_USER_DATA=<tmp dir> VORTAQ_SMOKE=1 VORTAQ_PLAIN_SECRETS=1 npx electron .` (exit 0 = renderer loaded, IPC answered, and the SQLite check passed: it creates a file in the scratch profile, opens it in the utility process, runs a script and cancels a runaway CTE in under a second; with `VORTAQ_SMOKE_MONGO_URL` or `VORTAQ_TEST_MONGO_URL` it also checks a MongoDB connection: shell commands through the bundled parser, Int64 kept, killOp cancel). Always use `VORTAQ_USER_DATA` for manual runs so the real profile and LaunchAgents are untouched.

## Layout

- `src/shared/` — domain types (`types.ts`), the typed IPC contract (`ipc.ts`), engine descriptors and capability flags (`engines.ts`; every engine has a driver and is offered in the connection pickers: `mysql` and `mariadb` share the mysql2 driver; there is no preview flag any more (the 2.0 «Motores en vista previa» setting is ignored and dropped from settings.json by `SettingsRepo`), see `docs/multi-engine-design.md`; `capabilities.ai` says which structure reader the AI assistant uses, whether it can EXPLAIN and what «Toda la conexión» covers), the MongoDB shell layer (`mongo/`: `shell.ts` the whitelisted query-tab grammar on acorn, never eval'd; `classify.ts` the guard pair `analyzeMongoWrites` (renderer allowlist) / `isObviousMongoWrite` (main denylist) plus `valueHasWriteStage` for parsed pipelines; `shellFormat.ts` canonical Extended JSON ⇄ shell text that round-trips every BSON type and the typed cell values; `uri.ts` «Pegar URI» / «Copiar URI», refusing credentials in parameters) connection validation shared by main and the dialog (`connectionValidation.ts`) and the SQL dialects (`dialects/`: splitting, both production-guard classifiers and quoting; `mariadb.ts` wraps the MySQL functions untouched and adds `/*M!` comments, sequence functions and `SET STATEMENT … FOR` to both guards; `mysql.ts` holds the v0.1.0 functions moved verbatim and pinned by `dialects/golden/mysql.json`, whose outputs must never be regenerated from the code under test; the old paths `main/mysql/sqlSplit.ts`, `shared/sqlSplit.ts`, `shared/productionGuard.ts`, `renderer/.../query/writeGuard.ts` and `renderer/.../utils/sql.ts` re-export them for one phase). **The IPC map is the only API between renderer and main.** Add a channel there first, then implement `src/main/ipc/<area>.ts`, then use it from the renderer through `window.vortaq.invoke`.
- `src/main/` — Electron main. Modules: `db/` (engine-neutral layer: `driver.ts` interfaces, `registry.ts` engine → driver with lazy imports, `manager.ts` ConnectionManager with open dedupe/secrets/SSH tunnel/fatal/closeAll and the MySQL-only `getSessionFactory` for backups and jobs, `errors.ts` `DbUserError`/`ServerError`/`describeForLog`/capability gates, `tunnel.ts`, and the generic `query.ts`/`tableData.ts`/`rowChanges.ts` loops), `navicat/` (import), `postgres/` (the PostgreSQL driver: `client.ts` builds pg clients with every connection parameter explicit and the password as a function, never PG* env vars or ~/.pgpass, plus the libpq SSL plan; `connection.ts` keeps one pool per database (`closeDatabaseFromTree` behind `db:closeDatabase`), the query tabs' sessions (`TabSession`, D12) and the running executions for `pg_cancel_backend`; `introspect.ts` reads pg_catalog only and rebuilds table DDL; `query.ts` runs one statement at a time through pg-cursor and resolves result columns to their table by RowDescription tableID/columnID; `values.ts` parses only bool/int/float and keeps every other value as server text; the db:* handlers are `ipc/dbPostgres.ts`, which refuses a plain-string SchemaRef and runs guarded connections' sessions read-only), `sqlite/` (the SQLite driver on Electron's built-in `node:sqlite`, no native module: `core.ts` is the pure node:sqlite logic that runs inside the worker (opens through a `file:` URI with mode=rw/ro so **opening never creates a file**; only `createSqliteFile`/`sqlite:createFile` uses mode=rwc and refuses an existing file; an authorizer denies `ATTACH` of a missing or relative path; values keep their storage class with `setReadBigInts`), `worker.ts` is the `utilityProcess` entry (electron-vite input `sqliteWorker`), `spawner.ts` the injected `ProcessSpawner` (`electronSpawner.ts` is the only file that imports Electron; tests use `inProcessSpawner`), `client.ts` the RPC with kill-based cancel, `connection.ts` one worker and one handle per connection behind a lock: query tabs share it, the tab that opens a transaction owns it and other tabs' writes are refused, guarded connections run with `PRAGMA query_only = ON` until a confirmed write; `introspect.ts` reads sqlite_schema and the pragma table-valued functions; `query.ts` marks result columns editable by rowid (or the key of WITHOUT ROWID tables); `rebuild.ts` runs the designer's 12-step rebuild with the shared builder `shared/sqlite/rebuild.ts`; at most 4 open SQLite connections; the handlers are `ipc/dbSqlite.ts`, where the string SchemaRef is the attached database alias), `mongo/` (the MongoDB driver on the official `mongodb` package: `client.ts` builds MongoClient options with credentials in `auth` only (never in the URI), Vortaq's timeouts, TLS servername through the SSH tunnel, zlib only, and `RAW_BSON` (no promotion) for every read that returns documents; `connection.ts` the client, query-tab sessions (`use` database, transactions on replica sets), «Cargar más» cursors (10 min idle, 5 per owner) and executions killed by `comment` with `killOp`; `values.ts` canonical EJSON out and shell-bson-parser (strict, named `parse` export: the default export breaks in the CJS bundle) / EJSON in, with parse errors shown but never logged (`MongoInputError`); `documents.ts`, `changes.ts` (edits by `_id`: `$set`/`$unset` with the original value of each path as optimistic check, replace only of documents fetched whole, transactions on replica sets), `admin.ts`, `run.ts` (prepares the whole script, parsing every argument and deciding writes from the parsed values, before running anything); the handlers are `ipc/mongo.ts` (`mongo:*` plus the shared db:* channels; every other db:* channel refuses a MongoDB connection), `mysql/` (the MySQL driver: `driver.ts` adapts the mysql2 pool to `db/driver.ts`; introspection, queries, row changes and their SQL; `manager.ts` and `tunnel.ts` are re-export shims for one phase), `backup/` (.vqb and .nb3 read/write/restore; `archive.ts` is the format-neutral entry every caller uses; `vqb/` holds Vortaq's own format: its ZIP container, scrypt + chunked AES-256-GCM, typed JSONL values, the MySQL adapter that lets `restore.ts`/`replace.ts` read a .vqb like an .nb3, and the PostgreSQL, SQLite and MongoDB backup/restore/REPLACE (one transaction; SQLite also restores into a new file and keeps each cell's storage class; MongoDB stores each document as canonical Extended JSON in a `$json` value, has no transactional DDL and takes a safety copy before REPLACE). The public spec is `docs/vqb-format.md`; its examples are parsed by `vqb/spec.test.ts`, keep both in sync and bump `formatVersion` for incompatible changes. Decrypted manifests are never written to the index cache), `automation/` (jobs, scheduler, launchd; a job's .vqb backup password is `CredentialStore` kind `backupKey:<jobId>`, never in jobs.json, logs or the renderer; every engine has jobs: per-engine step rules live in `shared/jobEngines.ts` (query steps and `.nb3`/`.sql` copies are MySQL/MariaDB only, PostgreSQL/SQLite/MongoDB copies are `.vqb`, a restore stays within one engine and never targets that engine's system databases); the runner replaces MySQL/MariaDB databases with `backup/replace.ts` and the other engines through `BackupService.replace`; `automation/targetDatabases.ts` lists their databases for «Restaurar todo»), `credentials/`, `storage/` (JSON repos in userData), `migration/` (one-time ElectronDB/Navidog -> Vortaq profile and secret migration), `updates/` (checks GitHub Releases for a newer version: notify only, never downloads or installs; network calls stay in main via `net.fetch`; `app:openExternal` only allows release pages and downloads of `https://github.com/Y0rshB3/Vortaq/releases/...` and of the repository's earlier name `…/Y0rshB3/ElectronDB/releases/...`), `ai/` (bring-your-own-key AI assistant: Anthropic adapter on the official `@anthropic-ai/sdk`, every other provider on the official `openai` SDK; provider calls go through Electron `net.fetch` from main only, keys live in `CredentialStore` kind `ai` and are never returned to the renderer). **AI privacy rule:** only database structure may reach a provider. The context builder reads metadata exclusively through `MetadataQueryable` (`ai/metadata.ts`), which refuses anything but `SELECT … FROM information_schema.*` / `SELECT VERSION()`; never send row values, query results, cell contents, connection hosts, users, passwords or names. PostgreSQL connections use `PgMetadataQueryable` (`ai/pgMetadata.ts`): one read-only SELECT whose relations are all `pg_catalog.*` / `information_schema.*`, checked with the PostgreSQL lexer and write allowlist. SQLite connections use `SqliteMetadataQueryable` (`ai/sqliteMetadata.ts`): one read-only SELECT whose sources are all `sqlite_schema`/`sqlite_master`/`sqlite_temp_schema` or the read `pragma_*` table-valued functions (table_xinfo, index_list, foreign_key_list…), checked with the SQLite lexer and write allowlist; its only other statement is `EXPLAIN QUERY PLAN` of a single SELECT on user action (`explainSqliteSelect`). MongoDB connections use `MongoStructureSource` (`ai/mongoMetadata.ts`), which has no query method: collection names, index keys, the structural part of a `$jsonSchema` (bsonType/required/properties/items/description) and sampled field paths with BSON types (values dropped in `shapeOf`); never view pipelines, partial filters, enum/pattern literals or documents, and no explain. The only other statement the assistant may issue is `EXPLAIN` (never `ANALYZE`) of a single SELECT on user action (`ai/explain.ts`, `explainPgSelect`). The assistant never executes SQL: generated SQL is only inserted into the editor. **Scope** (`AiScope`): «Solo <bd>» sends one namespace's structure and the others by name; «Toda la conexión» (also when nothing is selected) sends every user namespace (`AiService.namespaces`: MySQL/MariaDB/MongoDB databases without the system ones, the schemas of the current PostgreSQL database, SQLite main and its attachments) as `namespace.table`, at most `MAX_CONTEXT_DATABASES` (40) with structure, MongoDB sharing a sampling budget; every namespace still goes through its engine's reader above. **Agents (MCP), a separate exception:** the built-in assistant's structure-only rule above is unchanged. `Vortaq --mcp` (`src/main/mcp/`) lets an external agent use only the connections the user enabled one by one (`ConnectionConfig.mcp`), and only while «Permitir que agentes usen Vortaq (MCP)» (`AppSettings.mcpEnabled`) is on, at the level chosen per connection: `structure` (no row values; MongoDB through `MongoStructureSource` rules), `read` (one statement `checkExportStatement` accepts, in a new read-only session; MongoDB provable reads only) or `write` (never on connections that need the typed confirmation, re-checked on every call, and never sent with `confirmProduction`). Rows an agent reads go to the agent's provider; hosts, ports, users, SSH settings, URIs and file paths never do (errors are redacted).
- `src/main/mcp/` — the MCP server of `Vortaq --mcp` (2.1.0, stdio only, official `@modelcontextprotocol/sdk`). Electron-free (ESLint core boundary): `server.ts` (tools `list_connections`, `list_databases`, `list_tables`, `describe_table`, `run_query`, `explain_query`, `execute_sql`, the checks every call runs and one activity line per call in `logs/mcp.log`, never SQL or values), `runtime.ts` (read-only profile context, same db:*/mongo:* handlers through a `HandlerRegistry`, reopens a connection whose settings changed, closes idle SQLite workers past `MAX_OPEN_SQLITE`), `tools.ts` (`run_query` reuses `openRowSource` from `export/sources.ts`; MongoDB scripts refuse `rs.*`, serverStatus/currentOp, server stages and the system databases, explain/stats answers drop host keys, and describe_table (like the AI context, `shapeOf` with `collapseDataKeys`) shows keys that are data as `<clave>`; SQLite `execute_sql` refuses ATTACH/DETACH/VACUUM), `access.ts` (levels and refusals), `redact.ts` (every error message, also bare host names of driver errors; secrets, non-loopback hosts, file paths and cells that are the account itself also from answers), `values.ts` (JSON-safe cells, 100/1000 rows, 30/120 s server-side timeout, 2,000-char cells, ~200 KB responses), `profile.ts` (refuses while a legacy migration is due; never migrates). The rules shared with the UI are `shared/mcp.ts` (levels, effective level, client snippets: Claude Code, Claude Desktop, Codex, Gemini CLI, Antigravity, Cursor, VS Code, OpenCode and «Otro cliente»; any client that starts local stdio MCP servers works, web apps cannot). The Electron side is `main/mcpStdio.ts` (first import of `index.ts`: stdout carries only JSON-RPC) and `main/mcpMain.ts` (no window, menu, scheduler, update check or migration; Chromium data in a scratch folder except Windows' `userData`; `JsonStore` reload + read-only modes; exits when stdin closes). UI: `renderer/.../components/mcp/` (Ajustes section: every saved connection with its own switch and level, staged and saved with «Guardar» through `connections:setMcp`, which changes only `mcp`/`updatedAt` and refuses «Lectura y escritura» where typed confirmation applies; the connection dialog tab; both hidden in the editor extension). Tests: `tests/integration/mcp*.test.ts`, end to end `npm run test:mcp-e2e` after `npm run build` (scratch profile only); screenshots `VORTAQ_SHOTS_ONLY=49` (needs `scripts/seed-mcp-shots.mjs`).
- `src/preload/` — contextBridge only, no logic.
- `extensions/vscode/` — the editor extension «Vortaq» (VS Code 1.123+, Cursor, VSCodium, Windsurf; id `y0rshb3.vortaq`, its own version 0.x and tags `vscode-v*`, never marked «latest» on GitHub because the desktop update check reads `/releases/latest`; each extension release also updates the versioned `.vsix` links in the README header and «Instalar la extensión»). A separate npm project (not a workspace: the desktop lockfile and electron-builder stay untouched): `npm run ext:install|ext:build|ext:test|ext:package`; `npm run check` also lints, typechecks and unit-tests it with a mocked `vscode`. `src/host/` wires `createCore()` (profile in `globalStorageUri`, secrets with `keyCodec` and the vault key in SecretStorage, `nodeSqliteSpawner`, SQLite hidden when `sqliteRuntimeProblem()`), the TreeView, per-document connection/database targets for `.sql` files, the typed-name production prompt (`guard.ts`) and the webview panels (the results panel's «Exportar» in `panels/exports.ts`: VS Code's save dialog for `app:pickSaveFile`, `export:*` only for the file just chosen and the panel's own connection, progress to the webview and `window.withProgress`); `src/protocol.ts` whitelists and validates every host ⇄ webview message (JSON-safe values); `src/webview/` reuses the renderer's Vue components with `--vscode-*` colours mapped onto `--nd-*`. Desktop import (`desktopImport.ts`) reads only Vortaq's own `connections.json`, never passwords. Integration tests run in a real VS Code downloaded to `~/Library/Caches/vortaq-vscode-test`. Design, as-built notes and the phase list: `docs/vscode-extension-design.md`.
- `src/core/` — the Electron-free core for the editor extension (and any Node host): `index.ts` re-exports what an extension needs from `src/main`/`src/shared` and `createCore()` (`host.ts`), whose `invoke()` answers the connections/db/sqlite/mongo/filters/backups/export/ai channels behind the same production guard as the desktop. Host-specific pieces are ports: IPC handlers register through `HandleFn` (`ipc/router.ts`; the desktop passes the ipcMain one), AI network calls through `setAiFetch` (desktop: `ai/electronFetch.ts`), the SQLite worker through a spawner (`electronSpawner.ts` or `nodeSqliteSpawner`; `sqliteRuntimeProblem()` says whether the host's Node can run it: Node ≥ 24.10), secrets through a `SecretCodec` (desktop `credentials/electronCodec.ts` = safeStorage; extension `keyCodec` with a key in the editor's SecretStorage). **Nothing reachable from `src/core/index.ts` may import `electron`, `electron-updater` or a desktop-only file:** ESLint forbids it in the core folders and `npm run check:core` / `scripts/core-bundle.test.ts` bundle the core with esbuild and fail on it; `tests/integration/coreNode.test.ts` runs the bundle in plain Node against every engine. Design and phase plan: `docs/vscode-extension-design.md`.
- PostgreSQL addressing: every object channel takes `SchemaRef` `{ database, schema }` (build it with `utils/schemaRef.ts`; MySQL keeps the plain database string). PostgreSQL tree ids carry the database as one trailing segment (`d:<conn>:<db>` database nodes), and its tabs set `tab.database`; MySQL ids, tabs and titles are unchanged.
- `src/renderer/` — Vue 3 + Vuetify 3 + Pinia. Views under `src/views`, reusable components under `src/components`, stores under `src/stores`, `src/api.ts` wraps `window.vortaq`. `src/engines/` is the engine UI registry: `mysql.ts` points at today's designer/DDL/user-SQL/editor modules (views reach them through `useEngineUi`), `postgresql.ts` and `sqlite.ts` at their own (SQLite: `components/designer/sqlite/planner.ts`, `designer/sqliteDdl.ts`, `editor/sqliteCompletion.ts`), `capabilities.ts` (`can`, `groupsFor`, `descriptorOf`) drives menus, toolbar, tree groups and the backup/job pickers. MongoDB has no `EngineUi` (no SQL dialect): its tabs are `collection` (`views/CollectionView.vue`), `collectionDesigner` (`views/CollectionDesignerView.vue`) and the `query` kind routed by `views/QueryRouterView.vue` to `views/MongoQueryView.vue`; the documents UI lives in `components/mongo/` (`docModel.ts` holds the staging rules: whole-array `$set`, no `_id` or dotted/`$` keys by path, `expected` originals) and the editor completion in `editor/mongoCompletion.ts`; the tree's MongoDB database is a `schema` node (like MySQL) with groups `collections`, `views`, `indexes` (index nodes are named `<collection>.<index>`). Read neutral metadata (`typeKind`, `primary`, `kind`, …) through `utils/columnMeta.ts`, which falls back to the MySQL checks. Tree node ids are `:`-joined percent-encoded segments: build them only with `nodeIds`. MySQL menus and toolbar are pinned by `__tests__/__snapshots__/mysqlMenus.test.ts.snap`; never regenerate it to make a change pass.
- Job editor (`views/JobEditorView.vue`, 2.0.1): header + sections Pasos/Programación/Opciones/Historial; `components/automation/JobStepList.vue` (sequence: drag, Alt+↑/↓, per-step problems from `jobForm.taskProblems`), `JobStepSettings.vue` (every step option), `JobStepBrowser.vue` + pure `jobSteps.ts` («Añadir pasos»: kinds, connection › database, items that become ordinary `JobTask`s; opens a connection only when the user picks it), `CopyRestoreDialog.vue` + pure `shared/jobRecipes.ts` («Copiar y restaurar»: backup steps of an origin's databases, then one «Restaurar paquete» step or restore steps of «la copia del paso N» into a destination; also run end to end by `tests/integration/copyRestoreRecipe.test.ts`). The only step kind added in 2.0.1 is `restorepackage` («Restaurar paquete», rules in `shared/restorePackage.ts`, latest package of a job in `main/automation/jobPackages.ts` and `jobs:packages`): this job's copies or another job's latest package into one target; the runner checks the whole package first, then replaces the step by one ordinary restore per database (run entries carry `packageStepId`), so every restore guard applies to each; end to end in `tests/integration/restorePackage.test.ts`. Design and rules: `docs/job-editor-design.md`. Its screenshots (`VORTAQ_SHOTS_ONLY=45`, «Copiar y restaurar» and «Seleccionar todo» `46`, «Restaurar paquete» `47`) need `scripts/seed-automation-shots.mjs`.
- Copy/export of results (2.0.2): `src/shared/export/` holds the pure formatters (TSV/CSV, JSON, INSERT/UPDATE/IN with each engine's quoting and the `0xHEX`/storage-class literals, Markdown, HTML, the XLSX worksheet XML) and `checkExportStatement` (one statement, returns rows, read-only for the dialect's allowlist); `src/main/export/` writes files through `<file>.part` (renamed when complete, deleted on failure or cancel; XLSX deflates a temporary sheet into the package with `ZipWriter.addFile`, `.vqb` entries stay STORED) and, for «Resultado completo» (`export:query`), re-runs the statement or the table view's SELECT (filter and sort, no paging) in a NEW read-only session: MySQL/MariaDB `START TRANSACTION READ ONLY` + `KILL QUERY` to cancel, PostgreSQL `BEGIN READ ONLY` + `pg_cancel_backend`, SQLite a separate worker opened `mode=ro` + `query_only` (`openReader`, never the tabs' handle; cancel kills it). Reading needs no typed confirmation; nothing on this path may write. MongoDB is refused. The grid selection model is `renderer/.../data/gridSelection.ts` (cells, gutter rows, header columns, all): rows for «Eliminar» come only from the gutter or the active cell (`rowsForDeletion`), never from a column selection or select-all; copy text is `data/gridCopy.ts`, the dialog `data/ExportDialog.vue`. `EditableResult` offers «Exportar» only with `exportable` (the desktop query view and the editor extension's results panel, whose host answers `app:pickSaveFile` and `export:*`). Integration: `tests/integration/exportResults.test.ts`; screenshots `VORTAQ_SHOTS_ONLY=48` (needs `scripts/seed-screenshots.mjs`).
- MariaDB (P5): the `mariadb` engine uses the mysql2 driver (`registry.ts`), with `mariadbDialect` on its connections and in `db:execute`; `src/main/mysql/authPlugins.ts` holds the `client_ed25519`/`parsec` sign-in (offered to every MySQL-family pool; a MySQL server never asks for them), `src/main/mysql/mariadb.ts` the MariaDB-only SQL (sequences, JSON-as-LONGTEXT detection, P1b fixes, and the backup helpers: `.vqb`/`.sql` carry sequences and versioned history, `.nb3` only current rows and no sequences, and `replaceSafetyPlan` makes a REPLACE's safety copy a `.vqb` when the database has such objects), `components/designer/mariadb/planner.ts` the designer (uuid/inet types, system versioning) and `engines/mariadb.ts` the renderer engine. `ConnectionsRepo` lets `mysql` become `mariadb` and never back (`promoteToMariaDb`); `migration/mariadbEngine.ts` promotes imported MariaDB entries at startup and `db/manager.ts` a `mysql` connection whose server reports MariaDB when it opens (never headless). MariaDB servers behind a `mysql` connection still get the P1b fixes: `src/shared/serverFlavor.ts` detects the flavour from `VERSION()` (also `ServerInfo.runtime.flavor`) and every fix is gated on the session's `serverVersion` (`isMariaDbSession`), so a MySQL server never sees new SQL; keep it that way (MySQL SQL literals are checked for parity against the previous release).
- `src/main/importers/navicat/ncxCipher.ts` — password decoding for `.ncx` files the user exports with Export Password; used only by the `.ncx` importer (`src/main/importers/connections/`), and only for a file the user picked. Importers never read third-party credential stores (DBeaver credentials-config.json, OS keychains, Windows registry).
- `src/main/licenses.ts` + `scripts/third-party-licenses.mjs` — LICENSE and the generated `THIRD_PARTY_LICENSES.txt` (written to `out/` by `npm run build`, shipped as extraResources, shown in «Acerca de Vortaq»).
- `tests/fixtures/navicat/` — synthetic files written to the observed Navicat layout + a synthetic `.nb3` (see its README). Never add real hosts, users or data.
- `docs/navicat-storage.md` — verified Navicat formats. Read it before touching import/backup code.
- `docs/research/` is git-ignored and must never be committed: working notes there may describe third-party binaries. Design docs cite only the user's own files, the official `.ncx` export and public documentation.

## Naming and the legacy names (ElectronDB, Navidog)

- Product name and identifiers live in `src/main/brand.ts` (`APP_NAME`, `LEGACY_APPS` newest first, `UPDATE_REPO`); env switches are read with `envVar()` (`src/main/env.ts`): `VORTAQ_<NAME>`, with `ELECTRONDB_<NAME>` and `NAVIDOG_<NAME>` accepted as undocumented fallbacks.
- Keep the old names only where they identify legacy data or a stable identifier: `src/main/migration/`, `LEGACY_APPS` (profile folders, "ElectronDB Safe Storage" / "Navidog Safe Storage" keychain items, `dev.y0rshb3.electrondb.job.*` / `dev.y0rshb3.navidog.job.*` launchd labels), the env fallbacks, the `appId` `dev.y0rshb3.electrondb` (Windows installer GUID and macOS bundle id: never change it, see `electron-builder.yml`), the repository's earlier name `Y0rshB3/ElectronDB` (`LEGACY_UPDATE_REPOS`, still accepted by `isAllowedReleaseUrl`; the feed itself is `Y0rshB3/Vortaq`: `UPDATE_REPO`, `publish`), the localStorage keys `electrondb.*` (saved queries, column widths...; `navidog.queries.*` is adopted once), the backup source value `'electrondb'`, the test compose project `electrondb-test`, and the throwaway test MySQL credentials (`root`/`navidog`, db `navidog_test`).
- CSS tokens and utility classes keep the internal `--nd-*` / `nd-` prefix on purpose (it stands for the oldest name); do not rename them.
- Migration runs once per profile: `runProfileMigration` before app `ready` copies the newest legacy profile (`<appData>/ElectronDB`, else `<appData>/Navidog`) into `<appData>/Vortaq`, never overwriting and never deleting, and writes `migrated-from-<name>.json` (`*.json`, `logs/`, `Local Storage`, `ai/`; on Windows also `Local State`; never `backups/`, which stays in use where it is). `runSecretMigration` runs right after the context: it re-encrypts `credentials.json` (passwords and AI keys); on macOS it reads the old safeStorage keys with `security`, ElectronDB's first and Navidog's only for values the newer key cannot decrypt. Old launchd agents of jobs present in the new profile are replaced by `dev.y0rshb3.vortaq.job.*` ones. A one-time info notice says the data moved. On macOS, after a migration from ElectronDB, a one-time notice offers «Mover ElectronDB a la Papelera» when `/Applications/ElectronDB.app` or `~/Applications/ElectronDB.app` is still installed (both apps share the bundle id): `migration/legacyApp.ts` finds it (Info.plist executable `ElectronDB`, never the running app) and `app:trashLegacyApp` calls `shell.trashItem` only after the user clicks. A scratch profile (`VORTAQ_USER_DATA`) skips it.
- Test-only switches, never for real use: `VORTAQ_NAVICAT_CANDIDATES=<dirs>` replaces the automatic Navicat folder search (screenshots/tests); `VORTAQ_LEGACY_USER_DATA=<dir>` migrates from that folder even into a scratch profile (its folder name, `ElectronDB` or `Navidog`, says which product wrote it); `VORTAQ_LEGACY_KEYCHAIN=<file>` reads the legacy "… Safe Storage" items from that keychain file instead of the login keychain. `VORTAQ_LEGACY_APP_PATHS=<bundles>` (path-delimiter list) replaces `/Applications`/`~/Applications` in the ElectronDB-app check (a scratch profile checks nothing else).

## Conventions

- Tests live next to code as `*.test.ts`; node-side tests must not import `electron`.
- Never log query data, passwords or backup contents. Secrets go through `CredentialStore` only.
- Never read another application's private data (keychain items, registry, caches): imports read only files the user owns and picks (Navicat's folder, `.nb3`, `.ncx`). UI texts and comments describe Vortaq's behaviour; do not describe features as "like"/"al estilo de" another product.
- Any operation that writes to a connection whose environment requires typed confirmation (`requiresTypedConfirm` in `src/shared/typedConfirm.ts`: always `production`, plus the environments listed in `AppSettings.typedConfirmEnvironments`) must require explicit confirmation: the UI dialog (`useConfirm().confirmDestructive`) and then `confirmProduction: true` in the IPC call (`WriteOptions`). Main enforces it in `src/main/ipc/productionGuard.ts`.
- Errors thrown from IPC handlers surface to the user as their `message`: write actionable messages.
